# 디버거 2인 병렬 개발 분업안

작성일: 2026-10-13  
상태: A의 Java 헬퍼와 B의 Python·MCP 구현을 연결했다. 단독 JVM 및 임시 Paper 서버에서 실제 MCP/JDI 흐름을 검증했으며 [B 구현·검증 안내](debugger-python.md)를 따른다. 기존 실행 서버와 사용자 IDE 호스트의 검증은 별도다.

## 1. 배경과 분업 결론

CraftMCP는 Minecraft 플러그인을 조사하기 위한 Python MCP 프로젝트다. 서버 기준은 Windows, Java 17, Paper 1.20.1 build 196이다. 디버거는 **게임 밖의 Java 헬퍼가 JDI로 서버 JVM에 연결**하는 방식으로 선정했다. DAP 어댑터와 게임 브리지는 이번 구현 범위에 없다.

RCON은 별도 팀원이 개발 중이다. 아래 **A와 B는 디버거 작업을 맡는 두 사람**이며, RCON 구현은 담당하지 않는다. 두 사람은 단독 Java 샘플과 수동 서버 콘솔 명령으로 개발·검증한다.

| 담당 | 개발할 부분 | 상대 구현 없이 개발하는 방법 |
|---|---|---|
| **A: Java·JDI 담당** | Java 헬퍼, JVM 연결, 중단점, 스택·변수, 재개·종료 | 단독 Java 샘플에 연결하고 JSON Lines 요청을 테스트 드라이버로 전송 |
| **B: Python·MCP 담당** | 헬퍼 프로세스 통신, MCP 도구, 증거 저장, Paper 재현 환경 | 계약에 맞는 모의 헬퍼를 구현해 요청·응답·이벤트를 시험 |

이 경계는 Java와 Python의 구현 파일을 분리하면서, 양쪽이 같은 통신 계약으로 독립 개발할 수 있게 한다. A의 실시간 디버깅 구현 부담이 크므로 B가 Paper 샘플과 MCP 통합 시험 준비를 맡는다.

먼저 [디버거 계획](debugger-plan.md)과 [통신 계약 v1](debugger-protocol.md)을 읽는다. 개발 순서와 소유권은 이 문서를, 메시지 형식은 통신 계약을 따른다. 기존 계획의 D0~D4는 기능 단계이며, 작업 배정은 아래 병렬 순서를 따른다.

## 2. 파일 소유권

아래 경로는 앞으로 만들 경로다. 기존 파일이 있다면 내용을 확인하고 보존한 뒤 수정한다.

| 파일·디렉터리 | 편집 담당 | 비고 |
|---|---|---|
| `debugger_helper/` | A | Gradle Wrapper, Java 소스, 단위·실제 JDI 통합 시험, 헬퍼 사용 안내 |
| `tests/fixtures/java_debuggee/` | A | Java 17 샘플, 디버그 정보 포함 빌드, 실행 및 입력 방법 |
| `mcp_server/adapters/debugger/` | B | 프로세스 통신, 모델, 요청 연결, 이벤트 수신 |
| `mcp_server/tools/debugger.py` | B | 디버거 MCP 도구 |
| `mcp_server/services/debugger.py` | B | 런타임 등록·경로 검증·증거 저장·수명 관리 |
| `tests/debugger_python/` | B | 모의 헬퍼, Python 계약 시험, Java 헬퍼 연동 시험 |
| `plugin_template/debugger_sample/` | B | Paper 콘솔 테스트용 샘플, 고정 입력·계산 결과 |
| `mc_server/start-debug.bat`, `mc_server/start-debug.sh` | B | 기존 일반 실행 스크립트와 별도의 JDWP 개발 실행 |
| `docs/debugger-java.md` | A | 빌드·실행·단독 JDI 검증 절차 |
| `docs/debugger-python.md` | B | 모의 헬퍼·MCP 실행·실제 Paper 검증 절차 |
| `docs/debugger-protocol.md` | B가 변경 취합, A가 검토 | 양쪽 구현에 영향을 주므로 일방적으로 필드 변경 금지 |

`pyproject.toml`, 공용 MCP 진입점·도구 등록, 공용 설정, `.gitignore`, `README.md`는 RCON 팀과도 공유되는 파일이다. B가 기존 구성을 확인한 뒤 필요한 최소 변경을 취합한다. RCON 담당자가 만든 코드나 의존성 설정을 덮어쓰지 않는다. 공용 진입점 연결 전에는 디버거 전용 실행 진입점으로 시험할 수 있다.

공유 문서 수정도 한 사람이 취합한다. 다른 담당자의 디렉터리에서 발견한 문제는 먼저 담당자에게 전달하고, 합의 후 담당자가 수정한다. 두 사람이 같은 파일을 동시에 수정하는 구조를 피한다.

## 3. A의 작업: Java 헬퍼와 실제 JVM 디버깅

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| A1 | Gradle·Java 17 프로젝트, JSON Lines 입출력, 준비 이벤트·버전 확인 | 계약 요청을 읽고 stdout에 메시지만 출력 |
| A2 | 반복 입력을 받는 단독 Java 샘플, JDWP 접속·detach | Python/MCP 없이 실제 JVM 접속과 종료 가능 |
| A3 | 클래스명·줄 중단점, 클래스 준비 이벤트, 중단 상태·재개 | 미로딩 중단점이 적용되고 계산 이후 멈춤 |
| A4 | 스택·인자·지역 변수·객체·배열 조회, 페이지와 참조 수명 | 알려진 계산 결과 조회, 재개 후 이전 참조 거절 |
| A5 | 중단 기한, 추가 이벤트 정리, stdin EOF·shutdown·VM 종료 처리 | 정상 종료·자동 재개를 증거와 함께 확인 |

A가 발급·관리하는 값은 `session_id`, `stop_id`, `thread_id`, `frame_id`, `object_ref`, `breakpoint_id`, 이벤트 순번이다. JDI 중단 상태와 참조의 최종 판단도 A의 헬퍼가 맡는다. B가 별도로 동일 상태 머신을 만들도록 요구하지 않는다.

단독 샘플은 계산 전후에 실행 가능한 줄을 분리하고 고정 입력에 대한 기대 결과를 문서화한다. 샘플을 수정하면 중단점 줄도 변경되므로 실제 클래스명과 줄을 `docs/debugger-java.md`에 갱신한다. Windows에서 샘플 JVM과 헬퍼를 별개 프로세스로 실행하는 절차를 제공한다.

배포 산출물은 `debugger_helper/build/libs/craftmcp-debugger-helper.jar`로 고정한다. 의존성이 있다면 포함해 `java --add-modules jdk.jdi -jar <절대 JAR 경로>`로 실행할 수 있게 한다. Python에서 문자열 셸 명령을 조합할 필요가 없도록 추가 필수 인자를 두지 않는다.

## 4. B의 작업: Python 통신·MCP와 Paper 시험

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| B1 | 계약 메시지 모델과 모의 헬퍼 | Java 구현 없이 정상 응답·중단·자동 재개·오류·프로세스 종료 재현 |
| B2 | 헬퍼 실행·종료, stdout/stderr 독립 수신, 요청 ID 연결 | 응답 사이에 이벤트가 와도 구분하고 진행 중 요청을 종료 처리 |
| B3 | 최소 MCP 도구, 런타임 등록, 경로 검증, 증거 저장 | 모의 헬퍼로 실제 MCP 호출 흐름 완료 |
| B4 | Paper 샘플 플러그인, 개발 실행 스크립트, 재현 안내 | RCON을 끄고 수동 콘솔 명령으로 고정 계산 결과 출력 |
| B5 | 실제 Java 헬퍼 연결, Paper 수동 재현, 통합 증거 | 중단·조회·재개 후 명령 정상 종료 |

B는 런타임의 JDWP host/port, 프로젝트 경로, 실행 JAR 경로, 소스 리비전·JAR 해시 등을 설정으로 관리한다. MCP `attach_debugger`의 `runtime_id`와 `project_id`를 검증한 뒤 헬퍼의 접속 인자로 변환한다. 외부 에이전트가 임의 실행 명령을 지정하는 도구는 만들지 않는다.

MCP 도구는 [디버거 계획 6절](debugger-plan.md#6-최소-mcp-도구)의 8개를 제공한다. 공용 FastMCP 설정이 있으면 재사용한다. 없다면 호환 버전을 확인해 잠그고 디버거 등록 함수를 분리한다. 공용 앱의 시작·종료 훅은 RCON 도구와 함께 사용할 수 있도록 최소 변경한다.

Python은 세션·중단 ID를 다시 발급하지 않는다. 헬퍼의 이벤트를 저장하되 `get_debug_state`는 헬퍼에서 현재 상태를 조회한다. 이벤트가 LLM을 자동 실행한다고 가정하지 않는다. 모의 헬퍼는 시험 전용이며 실제 JDI 결과를 제공한 것으로 보고하지 않는다.

## 5. 동시에 진행하는 순서

| 시점 | A | B | 연결 확인 |
|---|---|---|---|
| 시작 | 계획·계약 확인, Java 프로젝트와 샘플 준비 | 계획·계약 확인, Python 모델과 모의 헬퍼 준비 | 계약 v1에서 부족한 필드를 먼저 정리 |
| 병렬 1 | 실제 attach·중단·재개 구현 | 모의 헬퍼로 프로세스 통신·MCP 구현 | 준비 이벤트와 기본 응답을 먼저 실제 연결 |
| 병렬 2 | 스택·변수·참조 수명·종료 구현 | Paper 샘플·증거·오류 전달 준비 | 실제 Java 샘플에서 8개 도구 흐름 확인 |
| 공동 통합 | JDI 위치·변수·재개 문제 수정 | MCP·Paper 실행 및 결과 저장 문제 수정 | 실제 Paper 수동 명령 검증 |

처음부터 모든 Java 기능이 완성될 때까지 Python 작업을 미루지 않는다. 반대로 모의 시험만으로 완료하지 않는다. 최소 접속 흐름이 나오면 실제 프로세스를 연결해 인코딩·메시지·종료 문제를 조기에 확인한다.

## 6. 통합 완료 판정

1. Java 헬퍼를 정해진 JAR 실행 방식으로 시작하고 준비 이벤트를 확인한다.
2. 실제 JVM에 attach하고 클래스명·실행 줄 중단점을 등록한다.
3. 단독 샘플 또는 Paper 서버 콘솔에서 고정 입력의 동작을 실행한다.
4. 중단 ID를 얻고 스택·인자·계산 이후 변수·필드를 조회한다.
5. 실행을 재개하고 명령의 정상 종료와 기대 계산 결과를 확인한다.
6. 이전 프레임·객체 참조가 거절되는지 확인한다.
7. 중단 기한 만료, stdin EOF, VM 종료에서 상태와 pending 요청이 정리되는지 확인한다.
8. 실제 MCP 호스트에서도 위 조사 흐름을 반복하고 증거를 남긴다.

증거에는 사용 버전, 소스/JAR 식별 정보, 실행 방법, 입력·기대값·관찰값, 중단 위치, 정상 재개 또는 실패 사유를 기록한다. 환경이 없어 실제 시험을 못 했다면 모의 시험 성공과 실제 시험 미검증을 구분한다. RCON 응답·게임 체력·화면 검증은 이 완료 판정에 포함하지 않는다.

## 7. 계약 변경과 막힘 처리

- 새 필드·동작이 필요하면 이유, 메시지 예시, 양쪽 수정 범위를 통신 계약에 먼저 정리한다.
- B가 계약 변경을 취합하고 A가 확인한 뒤 양쪽 구현과 시험을 함께 갱신한다. 담당자 간 합의로 처리하며 사용자의 재승인을 기다리는 절차는 아니다.
- 상대 구현이 늦으면 모의 헬퍼 또는 단독 드라이버로 계속 개발하고 미검증 통합 항목을 기록한다.
- 호환되지 않는 변경은 `protocol_version`을 올린다. 버전이 다르면 접속을 거절하며 조용히 다른 형식으로 해석하지 않는다.
- 각자 작업 종료 시 수정 파일, 완료 기능, 시험 결과, 실제 서버 검증 여부, 상대에게 필요한 다음 조치를 보고한다.
