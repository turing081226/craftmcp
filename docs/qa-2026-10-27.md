## 수정 필요: RCON 호출의 무한 대기 (높음)

호출 위치는 `mcp_server/server.py:20`의 MCRcon 접속과 21행 command 호출이다. 선언된 mcrcon 0.7.0 구현은 Windows에서 socket timeout을 설정하지 않고 Unix signal 타이머도 사용하지 않는다. 또 `_read`는 `recv()`가 빈 bytes를 반환하는 EOF에서도 빠져나오지 않는다. 따라서 서버 무응답은 기한 없는 블로킹으로, 중간 연결 종료는 종료되지 않는 읽기 루프로 이어질 수 있다. 비밀번호나 명령은 이번 시험에서 고정된 가짜 값만 사용했다.

권장 수정은 connect/read에 유한한 기한을 적용하고 EOF를 즉시 연결 오류로 처리하는 RCON 어댑터다. async 호출에 timeout만 씌우면 내부 동기 스레드가 계속 남을 수 있으므로 소켓·작업 정리까지 확인해야 한다. 수정 후 같은 장애 시험에서 제한 시간 안에 MCP 오류를 반환하고 반복 호출 후에도 스레드·소켓이 누적되지 않는 것을 통과 기준으로 삼는다. 이번 요청에서는 QA와 재현 자료를 추가했으며 제품 수정은 하지 않았다.

## 재현

Java 17을 선택하고 저장소 루트에서:

```powershell
$env:JAVA_HOME = 'C:\Users\OWNER1\.jdks\ms-17.0.18'
$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
$env:GRADLE_USER_HOME = Join-Path $PWD 'debugger_helper/.gradle-user-home'
.\debugger_helper\gradlew.bat -p debugger_helper --no-daemon test
```

Python 의존성을 설치한 뒤 Windows에서 실행한다. TCP 25575가 사용 중이면 드라이버가 bind 실패로 중단하므로 실제 서버를 끄거나 격리 환경에서 실행한다. 각 호출은 별도 MCP 프로세스이며 모의 서버는 루프백에만 바인딩한다.

```powershell
uv venv .venv --python 3.12
uv pip install --python .venv/Scripts/python.exe -r mcp_server/requirements.txt
.venv\Scripts\python.exe -u eval\qa_main.py
```

드라이버는 정상 사례에 `pass`, 알려진 두 장애 재현에 `defect-reproduced`를 출력한다. 종료 코드 0은 이 관찰 결과를 재현했다는 뜻이며 제품 전체 통과가 아니다.
