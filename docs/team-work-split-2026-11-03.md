## 2. 무엇을 언제 완료할 것인가

| 완료 단계 | 함께 입증할 흐름 | 이때 완료하지 않아도 되는 것 |
|---|---|---|
| **v0 — 첫 통합** | 실제 MCP 호스트 → RCON 명령 job → 실제 Paper 중단점 → 스택·변수 → 재개 → 최종 명령 응답 → 중단점 없는 재실행 | 자동 빌드·배포 전체, 최종 시험 플러그인 선정, 봇·화면 자동화 |
| **v1 — 제작·수정 반복** | 소스 수정 → 빌드 → 종료 확인 후 배포 → 초기 상태 복원 → 기능 실행 → 실제 상태 판정 | 대규모 서버 네트워크, 모든 플러그인의 범용 관찰, 클라이언트 모드 지원 |

기존 디버거 도구 8개와 RCON/로그/빌드/배포 도구 4개는 이미 있다. 모두 새로 만들지 않고 필요한 부분을 확장한다. 현재 공용 앱도 존재하므로 각자 별도의 최종 MCP 서버를 만드는 방식으로 분업하지 않는다.

핵심 선행 경로는 **B의 명령 job ↔ D의 디버거 통합**이다. A는 서버 대상 조회를 먼저 제공하고 C는 그동안 빌드 경로를 진행한다. 첫 통합을 위해 C의 자동 배포 완료까지 기다리지 않는다.

## 3. 시작 전에 함께 고정할 계약

처음에 이 절의 최소 계약과 예제 데이터를 합의한 뒤 네 사람이 병렬로 시작한다. 완전한 프레임워크를 먼저 만드는 것은 아니다. 계약 변경 시 제공자와 사용자가 함께 확인하고 예제·시험을 같은 변경에 갱신한다.

### 3.1 공통 계약과 소유자

| 계약 | 최소 내용 | 변경 취합 | 검토/사용자 |
|---|---|---|---|
| runtime | `runtime_id`, `project_id`, 서버/프로젝트 경로, RCON 접속 참조, JDWP 주소, managed 여부, 관찰 가능한 부팅 식별자 | A | B·C·D |
| job | `job_id`, 작업 종류, runtime/run/request ID, 단계·상태, 송신 여부, 기한, 결과/오류·출력 페이지 | B | A·C·D |
| build/deployment | build_id, 소스 식별자, JAR 경로·SHA-256, deployment_id, 이전 JAR, 부팅 연결 | C | A·D |
| run/evidence | run_id, 시각·순서, job/build/deployment/session/stop 연결, 원문 참조·미검증 범위 | D | A·B·C |
| 공통 오류·결과 | schema_version, result/error, observed_at, warnings, evidence_ids, unknown/unsupported 의미 | A가 취합 | 전원 |

초기 예제와 인터페이스는 이 문서에 덧붙여도 된다. 양이 커지면 `docs/tool-contracts.md`와 `mcp_server/models/contracts.py`를 A가 취합해 추가한다. 각자 같은 Runtime/Job 모델을 따로 정의하지 않는다. 공통 모델은 다른 서비스 구현을 import하지 않는 작은 데이터 계약으로 둔다.

### 3.2 먼저 합의할 내부 서비스 호출 형태

아래는 호출 역할을 설명하는 초안이며 확정 Python signature는 아니다. MCP 도구는 이 내부 서비스를 감싼다.

| 제공자 | 서비스 동작 | 사용처 |
|---|---|---|
| A | `runtime.resolve(id)`, `runtime.status(id)` | B·C·D가 같은 서버를 선택 |
| A | `runtime.start(id)`, `runtime.stop(id)`, 서버별 배타 작업 관리 | C의 배포, A의 관리 도구 |
| B | `jobs.submit(spec, operation)`, `jobs.get(id)`, `jobs.cancel(id)` | A·C·D의 장시간 작업 |
| B | 검증된 명령의 내부 실행과 명령별 결과 해석 | D의 상태 query/fixture 실행 |
| C | build_id로 산출물 조회, 배포/복구 실행 | C의 도구와 D의 통합 시험 |
| D | `debugger.release_runtime(id)`, 공통 run에 증거 추가 | A의 종료와 C의 배포, 전원의 결과 기록 |

- 서비스끼리는 내부 API를 사용한다. 서버 안에서 자신의 MCP 도구를 다시 호출하는 구조를 만들지 않는다.
- `start_server`/`stop_server`/`deploy_plugin` 등의 바깥 도구가 job을 하나 등록한다. 그 안에서 사용하는 start/stop 내부 서비스는 같은 queue에 새 job을 넣고 기다리지 않는다.
- 서버별 배타 작업은 A가 제공하고 C가 사용한다. 동일 잠금을 중복 획득하거나, 배포 job 뒤에 종료 job이 갇혀 서로 기다리는 상황을 시험한다.
- 명령 대기·서버 잠금이 디버거 조회·재개까지 막으면 안 된다. 로그/상태/작업 조회도 불필요한 변경 작업 잠금에 묶지 않는다.

### 3.3 ID·상태·시간 규칙

- `run_id`는 외부 에이전트/시험 driver가 생성한 상관 ID를 받는다. 전용 `create_run` MCP 도구는 필수로 추가하지 않는다. D는 ID 형식·보존 범위와 기존 debugger evidence run의 매핑을 정의한다.
- `request_id`는 변경 요청의 중복 방지 ID다. B가 같은 대상·종류·입력의 중복을 기존 job으로 연결하고, 같은 ID에 다른 입력은 거절한다.
- job 상태는 `queued`, `running`, `succeeded`, `failed`, `unknown`, `cancelled`로 시작한다. 기한 만료 자체가 실행 안 됨을 뜻하지 않는다.
- 송신 상태는 `not_sent`, `sent`, `confirmed`, `unknown`을 구분한다. 완료 판정이 불가능한 변경 명령은 자동 재전송하지 않는다.
- RCON 응답 수신, 명령 수준 성공, 게임 결과 assertion을 구분한다. 지원하지 않는 필드는 `unsupported`/unknown으로 표시한다.
- 명령 총 기한에는 디버거 중단·조회·재개 시간을 포함한다. 중단 lease보다 RCON 기한이 짧아 정상 디버깅이 실패하지 않도록 B·D가 함께 값을 정한다. 실제 Paper watchdog과의 관계도 확인한다.
- 모의 구현/실제 JVM/실제 Paper/실제 호스트/실제 클라이언트 결과를 구분해 기록한다.

### 4.3 독립 개발 방법과 완료 기준

처음에는 작은 시험 프로세스로 수명 관리를 검증하고, `jobs`와 `debugger.release_runtime`은 계약에 맞는 fake를 주입한다. 관리하지 않는 기존 Paper 서버를 임의 종료하지 않는다.

완료 기준: 같은 runtime으로 RCON/JDWP/폴더를 식별하고, 실제 관리 서버의 종료를 확인한다. 포트 열림을 게임 준비 완료로 표시하지 않으며 중단 상태 조회가 RCON 응답 대기에 갇히지 않는다. 부팅 ID를 관찰할 수 없으면 unknown으로 남긴다.

### 5.3 독립 개발 방법과 완료 기준

현재 회귀 시험의 모의 RCON 서버를 활용한다. A가 없어도 고정된 임시 runtime을 주입하고, D가 없어도 응답 지연/완료/EOF를 발생시키는 명령을 사용한다.

완료 기준: 명령 시작 도구가 즉시 job을 반환하고, `get_job`이 명령을 다시 보내지 않는다. 대기 중 디버거·조회 도구가 응답하며, 유실 후 변경 명령을 자동 재전송하지 않는다. 시험은 실제 loopback 소켓에서 종료·재사용까지 확인한다.

### 6.3 독립 개발 방법과 완료 기준

빌드는 독립 Gradle 프로젝트로 확인한다. 배포 시험은 실제 파일과 fake start/stop/status를 조합해 종료 확인 전에 교체하지 않는지 검증한다. 실제 시작·중지 구현을 C가 별도로 만들지 않는다.

완료 기준: 정확한 build_id의 JAR를 배포하고, 서버 종료를 확인한 뒤 교체한다. 새 부팅에서 대상 플러그인 활성화를 관찰한다. 실패 빌드의 이전 JAR나 plugins 출력의 비슷한 이름을 성공으로 오인하지 않는다. 롤백은 월드/DB 복원과 별개임을 표시한다.

## 7. D — 디버거 통합·게임 검증·증거

### 7.1 담당 도구와 산출물

| 우선순위 | 도구/기능 | 책임 |
|---|---|---|
| P0 | 기존 디버거 도구 8개 연동 | runtime/job/run과 연결, 중단·조회·재개·해제 유지 |
| P0 | 공용 앱 연결·실제 통합 driver | 각 담당자의 등록 함수 취합, 공용 lifespan·동시 호출·종료 확인 |
| P0 | RCON 통합용 fixture | 명령 입력·완료 표식·중단점 위치·예상 변수 확정 |
| P1 | `get_game_state`, `reset_test_state` | 선택한 시험에 필요한 query·초기 상태 복원 |
| P1 | `get_run_evidence` | 명령·디버거·로그·빌드/배포·assertion 증거 연결 |
| P1 | `get_server_log`의 runtime/run 연결 | 기존 cursor 처리를 유지해 관찰·증거 서비스에 연결 |

디버거 8개는 `attach_debugger`, `set_breakpoint`, `remove_breakpoint`, `get_debug_state`, `get_stack_trace`, `get_variables`, `resume_execution`, `detach_debugger`다. 기존 Java 헬퍼를 다시 구현하지 않는다. 헬퍼 수정이 필요하면 D가 취합한다.

### 7.2 작업 순서

- [ ] D1: 기존 샘플과 독립 JVM/Paper 검증 경로를 확인하고 공통 run/디버거 evidence 매핑을 정의한다.
- [ ] D2: RCON 통합 fixture를 제공하고 B와 명령/파서 계약을 고정한다.
- [ ] D3: A의 runtime과 B의 job이 없어도 fake로 통합 driver·명령 대기 중 조회·재개 시험을 작성한다.
- [ ] D4: 제공되는 최소 실제 구현부터 공용 앱에 연결하고 실제 Paper에서 v0 흐름을 검증한다.
- [ ] D5: 실제 MCP 호스트에서 같은 흐름과 종료·lease 만료 복구를 확인한다.
- [ ] D6: 플러그인 선정 후 상태 query/fixture/assertion을 구현한다. C의 배포 정보를 증거와 연결한다.
- [ ] D7: 기능별 서버 로직 검증과 실제 플레이어/화면 검증 범위를 나눠 결과를 작성한다.

### 7.3 반드시 처리할 현재 샘플의 제약

현재 `DebuggerSamplePlugin`은 `ConsoleCommandSender`만 허용하고 다른 sender에 `LOCAL_CONSOLE_REQUIRED`를 반환한다. 따라서 현재 샘플을 그대로 RCON에서 실행할 수 있다고 가정하지 않는다.

D가 별도 통합 fixture 명령을 추가하거나 기존 명령의 허용 범위를 명시적으로 바꾼다. 기존 로컬 콘솔 시험의 의도를 보존하고, 허용/거절 sender와 실제 RCON 결과를 시험한다. 단순히 제한을 모두 제거하지 않는다. 샘플 변경 시 B의 명령 템플릿·파서와 중단점 줄 번호도 함께 갱신한다.

### 7.4 독립 개발 방법과 완료 기준

기존 `debugger_sample`과 수동 콘솔로 디버거를 검증하고, 명령 job은 fake로 연결한다. 시험용 상태·초기화 명령은 통신 fixture 범위부터 시작한다. 최종 게임의 마나/상점/팀 상태 등을 미리 확정하지 않는다.

완료 기준: 같은 실행의 RCON job이 실제 중단점에서 기다리는 동안 스택·변수를 읽고 재개하여 최종 응답을 받는다. 중단점 없는 정상 재실행도 통과한다. 공용 앱 종료 시 정리하고, 실제 게임 상태나 플레이어 입력을 확인하지 않은 부분은 미검증으로 남긴다.

## 8. 파일 소유권과 공유 파일 변경 규칙

아래 신규 경로는 제안이다. 모듈별 실제 파일명은 시작 시 확정하되, 같은 파일을 여러 명이 동시에 확장하는 구조는 피한다.

| 담당 | 주 편집 영역 | 본인 시험 |
|---|---|---|
| A | 신규 `services/runtime.py`, `tools/runtime.py`, 공통 계약/설정, 서버 실행 스크립트 | 신규 `tests/runtime/` |
| B | 기존 `adapters/rcon.py`, 신규 `services/jobs.py`, `services/commands.py`, `tools/commands.py`, `tools/jobs.py` | 기존 `tests/test_server_qa.py`, 신규 `tests/commands/`·`tests/jobs/` |
| C | 신규 `services/plugins.py`, `tools/plugins.py`, 일반 `plugin_template` 빌드 템플릿 | 신규 `tests/plugins/` |
| D | 기존 디버거 코드, `services/server_log.py`, 신규 game_state/evidence·각 tools, `plugin_template/debugger_sample/` | 기존 `tests/debugger_python/`, 신규 `tests/integration/`·`tests/game_state/` |

### 8.1 공용 server.py는 D가 취합

현재 `mcp_server/server.py`에 여러 구현이 들어 있다. A/B/C가 동시에 이 파일을 대규모 수정하지 않는다.

1. B와 C는 자기 기능의 추출 경로·등록 함수·기존 동작을 보존하는 패치를 준비한다.
2. D가 B/C와 함께 현재 `list_players`/`get_server_log`/build/deploy를 해당 모듈로 옮기는 작은 준비 PR을 취합한다. 기능 변경과 이동을 분리한다.
3. 각 담당자는 자기 `register_*_tools(mcp, services)`를 제공한다.
4. D가 공용 등록과 lifespan을 연결한다. 같은 이름의 도구 중복 등록·기존 도구 누락을 시험한다.

공용 앱 수정은 D가 맡지만 A/C의 독립 서비스·빌드 개발은 이 추출 완료를 기다리지 않는다.

### 8.2 나머지 공유 파일

- `pyproject.toml`·`uv.lock`·공통 설정/모델: A가 변경을 취합하고 영향받는 담당자가 검토한다. lock 파일을 각자 따로 재생성하지 않는다.
- 공용 `README.md`·실행 안내·최종 통합 결과: D가 취합한다. 개별 기능 문서·시험 결과는 각 담당자가 작성한다.
- `plugin_template/debugger_sample/`은 D, 일반 빌드 템플릿은 C가 담당한다. C가 템플릿 복사 방식을 바꿀 때 샘플 포함 범위를 함께 확인한다.
- 기존 통합 회귀 파일 `tests/test_server_qa.py`는 B가 취합한다. D가 로그 시험을 바꾸고 싶으면 B에게 요청하거나 D 소유 시험 파일로 분리한다.
- 다른 담당자의 파일에서 결함을 발견하면 재현·기대 결과를 전달하고 담당자가 수정한다. 서로의 변경을 임의로 덮어쓰지 않는다.

## 9. 병렬 진행과 합치는 순서

| 시점 | A | B | C | D | 공동 확인 |
|---|---|---|---|---|---|
| 시작 | runtime·공통 모델 초안 | job·명령 초안 | build/deploy 초안 | run·fixture·통합 초안 | 최소 계약·예제 응답·파일 소유권 합의 |
| 병렬 1 | 대상 조회·상태 | job+모의 RCON 명령 실행 | 독립 빌드·manifest/resources | fixture+기존 디버거·통합 driver | 각자 fake 기반 시험, 공용 추출/등록 준비 |
| 첫 실제 연결 | 고정 runtime 제공 | 최소 실제 명령 job | 빌드 보완 계속 | 실제 Paper의 중단·조회·재개 연결 | v0 흐름을 먼저 실행하고 막힌 구간 수정 |
| 병렬 2 | 관리 시작·종료·부팅 | 장애·취소·journal | 배포·상태·롤백 | 게임 query/fixture·증거 | 최소 기능부터 실제 서비스로 fake 교체 |
| 두 번째 실제 연결 | 관리 수명 안정화 | 공통 job 연동 | 실제 빌드→배포 | 실제 상태 assertion·호스트 재검증 | v1 제작·수정·재검증 반복 |

v0의 B↔D 연결은 자동 배포 없이 수동 설치한 고정 fixture로 시작한다. 반대로 v1에서는 fake와 모의 시험만으로 완료하지 않고 실제 관리 Paper에서 배포·게임 상태까지 확인한다.

특정 담당자의 일이 먼저 끝나면 다른 사람 파일에 바로 기능을 추가하기보다, 계약 시험·실제 통합 재현·검토를 지원한다. 담당자 변경이 필요하면 파일 소유권도 함께 갱신한다.

## 10. Git·PR·개발 환경 운영

- 각자 별도 브랜치/작업 사본을 사용한다. 브랜치 예: A `codex/runtime-lifecycle`, B `codex/command-jobs`, C `codex/plugin-build-deploy`, D `codex/debugger-integration`.
- 네 명 모두 시작 시 같은 기준 main과 계약을 확인한다. API가 바뀌면 다른 담당자가 추측해 따라가지 않도록 예제·변경점을 전달한다.
- 모든 작업을 끝낸 큰 PR 대신, 계약/독립 서비스/도구 등록/실제 통합을 작은 PR로 나눈다. 다른 미완성 브랜치 전체를 매번 합치지 않는다.
- 계약 초안만으로도 fake 기반 개발은 시작할 수 있다. 공통 계약과 최소 준비 PR은 먼저 합치고, 실제 서비스가 나오는 대로 D가 짧게 통합한다.
- 담당자별 서버 폴더·게임/RCON/JDWP 포트·월드·증거 폴더를 분리한다. 같은 PC면 가용한 임시 포트를 사용한다.
- 실제 통합 서버는 한 번에 한 사람이 사용한다. 종료·배포·중단점 시험 중 다른 사람이 같은 서버를 재시작하지 않는다.
- 각자 자기 환경의 `.env`·로컬 설정을 사용하고 비밀번호/월드/JAR/증거 원문을 공용 소스에 넣지 않는다.

PR에는 다음만 명확히 적는다: 구현 범위, 사용한 계약 버전, 본인이 실행한 시험과 증거, 실제 검증 범위, 미검증/의존 항목, 다른 담당자가 연결하는 최소 예시.
